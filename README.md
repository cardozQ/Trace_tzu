 # Trace Tzu

### The Art of Tracing Systems

> Know your system. Trace its behaviour. Find the bottleneck. Never become one.

**Trace Tzu** is an independent technical blog series exploring the art of understanding software systems.

We investigate what happens beneath the surface: system calls, kernel behaviour, application performance, instrumentation, and observability.

The goal is simple: understand how systems behave, learn how to investigate them, and discover what actually happens when software meets the operating system.

## What We Explore

- **Tracing & Observability:** Understanding system behaviour through tracing, logging, and metrics.
- **Linux Internals:** Exploring system calls, scheduling, memory, processes, and kernel behaviour.
- **eBPF & bpftrace:** Practical kernel instrumentation and dynamic tracing.
- **Performance Engineering:** Investigating latency, bottlenecks, overhead, and optimization.
- **Systems Debugging:** Learning to investigate problems instead of blindly guessing.
- **Instrumentation Research:** Understanding the trade-offs between visibility, accuracy, and overhead.

## The Approach

We believe technical learning doesn't have to be boring.

Trace Tzu combines:

- First-principles explanations.
- Real-world debugging scenarios.
- Hands-on experiments and reproducible labs.
- Code snippets and technical deep dives.
- Diagrams, analogies, and occasional memes.
- References to original documentation, research papers, and source code.

We aim to make complex systems concepts approachable without sacrificing technical depth.

## Repository Structure

- `articles/` - Technical articles and blog entries.
- `labs/` - Hands-on experiments and reproducible examples.
- `resources/` - References, tools, and reading lists.
- `assets/` - Diagrams and supporting material.

## Who Is This For?

Developers, system engineers, performance enthusiasts, Linux explorers, kernel hackers, and anyone curious about what happens beneath the applications they use.

Whether you're starting with tracing or digging into kernel internals, there's something here to explore.

## Philosophy

Measure before optimizing.

Understand before modifying.

Trace before guessing.

And remember:

**We wanted to find the bottleneck. We accidentally became one.**
